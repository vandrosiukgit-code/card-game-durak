# Context Report: card-game-durak

> Отчёт о состоянии проекта «Подкидной Дурак» (Walking Skeleton).
> Сформирован для быстрого погружения в контекст.

## 1. Общее описание

Проект представляет собой **walking skeleton** (минимальный сквозной каркас) сетевой
карточной игры «Подкидной Дурак». Реализован полный вертикальный срез:

- доменная модель карт (чистая бизнес-логика);
- транспортный слой на WebSocket (FastAPI);
- тестовая авторизация;
- простой веб-клиент (HTML + JS) для ручной проверки.

Игровая логика (правила ходов, взятие карт, определение победителя) **пока не реализована** —
эндпоинт `ACTION_MOVE` лишь подтверждает получение команды и рассылает системный лог.

## 4. Содержание модулей

### 4.1. `app/domain/cards.py`

Чистая доменная модель, изолированная от веб-фреймворков.

| Сущность | Тип | Описание |
|---|---|---|
| `Suit` | `StrEnum` | Масти: `HEARTS="♥"`, `DIAMONDS="♦"`, `CLUBS="♣"`, `SPADES="♠"`. Свойство `symbol`. |
| `Rank` | `IntEnum` | Ранги 6..14 (`SIX=6` … `ACE=14`). Свойство `label` → `"6".."A"`. |
| `Card` | `@dataclass(frozen=True, slots=True)` | Неизменяемая карта (`suit`, `rank`). `__str__` → `"A♥"`, `__repr__` → `Card(suit=HEARTS, rank=ACE)`. |
| `Deck` | класс | Колода из 36 карт. |

**API `Deck`:**

- `CARDS_IN_DECK: int = 36` — константа.
- `__len__()` — текущее число карт.
- `cards` (property) → `tuple[Card, ...]` — содержимое только для чтения.
- `shuffle()` — перемешивание (`random.shuffle`).
- `draw(count: int) -> list[Card]` — взять `count` карт сверху.
  - `ValueError`, если `count <= 0`.
  - `ValueError`, если `count > len(self._cards)`.

### 4.2. `app/transport/connection_manager.py`

Управление активными WebSocket-подключениями и тестовой авторизацией.

| Элемент | Описание |
|---|---|
| `ConnectionManager.USERS` | `{"player1": "123", "player2": "123"}` — тестовые учётки (в коде, не в БД). |
| `active_connections` | `dict[WebSocket, str \| None]` — сокет → логин (или `None`). |
| `connect(ws)` | `accept()` + регистрация как неавторизованного. |
| `disconnect(ws)` | Удаление сокета. |
| `authenticate(ws, username, password) -> bool` | Проверка пары и привязка `username` к сокету. |
| `get_username(ws) -> str \| None` | Логин авторизованного пользователя. |
| `broadcast(message: dict)` | Рассылка всем; при ошибке — `disconnect`. |
| `manager` | Глобальный синглтон `ConnectionManager()`. |

### 4.3. `app/main.py`

FastAPI-приложение `Durak Walking Skeleton`.

- **`@app.websocket("/ws")`** — `websocket_endpoint`:
  - `connect` → цикл `receive_json`;
  - `AUTH` → `authenticate` → `AUTH_SUCCESS` / `AUTH_FAIL`;
  - `ACTION_MOVE` → проверка авторизации → `broadcast` `SYSTEM_LOG`
    с временной меткой `HH:MM:SS`;
  - `WebSocketDisconnect` → `disconnect`.
- **`app.mount("/", StaticFiles(directory="app/static", html=True))`** —
  монтируется **последним**, чтобы не перехватывать `/ws`.

### 4.4. `app/static/index.html` + `app/static/app.js`

Тестовый стенд (тёмная тема, monospace):

- экран авторизации (`#auth-screen`) — логин/пароль, кнопка «Войти»;
- игровой экран (`#game-screen`) — кнопка «Сделать ход»;
- сетевой лог (`#log`) — вывод `SYSTEM_LOG`.

`app.js`:
- открывает `ws(s)://<host>/ws`;
- обрабатывает `AUTH_SUCCESS`, `AUTH_FAIL`, `SYSTEM_LOG`, `ERROR`;
- отправляет `{type:"AUTH", username, password}` и `{type:"ACTION_MOVE"}`.

### 4.5. `main.py` (корень)

```python
uvicorn.run("app.main:app", host="127.0.0.1", port=8000, reload=True)
```

### 4.6. `tests/test_cards.py`

Юнит-тесты `Deck` и `Card` (pytest):

- 36 уникальных карт, все комбинации масть×ранг;
- `draw` уменьшает колоду, берёт сверху, ошибки при `count<=0` и `count>len`;
- `shuffle` сохраняет состав;
- `str`/`repr` карты;
- иммутабельность `Card` (frozen).

## 5. Протокол WebSocket (JSON)

| Направление | `type` | Поля | Ответ сервера |
|---|---|---|---|
| C→S | `AUTH` | `username`, `password` | `AUTH_SUCCESS` / `AUTH_FAIL` |
| C→S | `ACTION_MOVE` | — | `SYSTEM_LOG` (broadcast) или `ERROR` |
| S→C | `AUTH_SUCCESS` | `username` | — |
| S→C | `AUTH_FAIL` | `message` | — |
| S→C | `SYSTEM_LOG` | `text` | — |
| S→C | `ERROR` | `message` | — |

## 7.1. Видение продукта (черновик, обсуждается)

**Конечная цель:** сетевая карточная игра «Подкидной Дурак» в браузере
(Google Chrome и другие современные браузеры), адаптивная под десктоп,
планшет и телефон. Сервер — self-hosted (локальный компьютер игрока),
клиент — браузер, связь по WebSocket.

**Требования к качеству (черновые, требуют уточнения):**

- современная графика и анимации (не текстовые карты);
- фоновая музыка и, возможно, звуки действий;
- кастомизация: стол, рубашка колоды, аватар, музыка.

**Зафиксированные решения:**

- **A. Аккаунты** — профиль сохраняется между сессиями (логин/пароль,
  аватар, выбранные стол/колода/музыка).
- **B. Кастомизация** — только готовые наборы (без загрузки своих ассетов).
- **C. Музыка** — одна фоновая композиция на весь сеанс.
- **D. Адаптивность** — первая версия только десктоп, но архитектура должна
  позволять расширение на планшет/смартфон без переписывания.
- **P. Комнаты** — один сервер поддерживает много параллельных партий.
  Разные компании игроков не видят друг друга.
- **Q. Хранение данных** — вариант (c): всё в БД (профили, статистика,
  активные партии).
- **T. Назначение БД** — только для статистики игр и сохранения пароля
  игрока. Ценных данных нет, личной и чувствительной информации не
  собираем.
  - **T.1. Хранение пароля** — открытым текстом или хеш (`bcrypt` /
    `hashlib`)? Не закрыто. Рекомендация ассистента: хешировать
    (базовая гигиена, 3 строки кода).
- **R. Регистрация** — логин/пароль. Только для идентификации перед другими
  игроками. Статистика по логину — на очень позднем этапе. Никакой почты,
  никакой финансовой информации. Минимальный функционал.
- **S. Безопасность** — минимальная. Данные пользователя особо не нужны.

**Открытые вопросы (см. обсуждение):**

- **E. Сервер** — только локальная сеть или доступ из интернета
  (проброс портов / туннель / хостинг)? Влияет на безопасность
  (реальные пароли, HTTPS/WSS, защита от подбора).
- **F. Звуки действий** — только фоновая музыка или ещё звуки
  (клик, ход, взятие, победа)? Нужны ли mute/громкость?
- **G. Кастомизация — детали** — оформление своё у каждого игрока или
  общее на стол? Сколько наборов в первой версии?
- **H. Аватар** — только картинка из набора или ещё имя/цвет/рамка?
- **I. Масштаб партии** — всегда 2 игрока (классический Дурак) или
  возможен вариант 3–4 («в кругу»)? Правила для 2 и 4 игроков разные.
- **J. Боты** — нужны для игры одному и для тестирования. Подпункты:
  - **J.1. Тип ботов** — (a) заполнители (ходят формально),
    (b) простые (знают правила, без стратегии),
    (c) умные (оценивают ситуацию, считают карты).
  - **J.2. Когда боты нужны** — в первой играбельной версии или позже?
  - **J.3. Где живут боты** — в домене (`app/domain/bot.py`) или
    в отдельном слое (`app/ai/`)?
  - **J.4. Как бот подключается** — как обычный игрок без WebSocket
    (сервер «ходит» за него) или как отдельный тип участника
    (`HumanPlayer` / `BotPlayer`)?
  - **J.5. Настройка ботов** — выбор сложности (лёгкий/средний/сложный)?
    Настройка внешнего вида (аватар, имя) — см. пункт G?
  - **Черновая рекомендация ассистента:** начать с J.1(a) —
    боты-заполнители, чтобы можно было тестировать игру одному,
    не требуя сложной логики. Умных ботов добавить позже,
    когда правила устоятся.
- **Стиль графики** — SVG-минимализм / реалистичные PNG / 3D (Three.js)?
- **Анимации** — раздача, полёт карты, переворот, взятие?

### 8.1. План проектирования архитектуры (milestone 2)

**Статус:** в работе. Обсуждение ведётся по карте темы
(см. `CONVENTIONS.md` §10). Текущий пункт — «Что из цели следует
для архитектуры».

**A. Доменные сущности** (что живёт на сервере):
- `Player` — игрок (человек или бот).
- `Room` — комната (название, видимость, макс. игроков, список игроков).
- `Game` — партия (колода, руки игроков, стол, чей ход).
- `Table` — стол (карты в атаке, карты в защите).

**B. Хранилище** (где живут комнаты и партии):
- Список комнат — в памяти или в БД?
- Активные партии — в БД (см. `VISION.md` §5, решение V).
- За каким интерфейсом? (Чтобы потом подменить на БД без переписывания.)

**C. Протокол сообщений** (что ходит между клиентом и сервером):
- Лобби: `LIST_ROOMS`, `CREATE_ROOM`, `JOIN_ROOM`, `LEAVE_ROOM`.
- Комната: `ROOM_STATE`, `PLAYER_JOINED`, `PLAYER_LEFT`, `GAME_STARTED`.
- Стол: `DEAL`, `PLAY_CARD`, `CARD_PLAYED`, `TAKE_CARDS`.
- Всё — Pydantic-схемы, не `dict` (см. `VISION.md` §8).

**D. Связь `ConnectionManager` ↔ комнаты**:
- Сейчас `broadcast` шлёт всем. Нужна адресная рассылка: только игрокам
  конкретной комнаты.

**Решение по границе «домен vs. транспорт» (пункт 3.0 карты):** ✅ ЗАКРЫТО.
Выбран **гибридный вариант (c)**:

- `Game`, `Player`, `Table` — в `app/domain/` (чистая логика, без сети).
- `Room`, `RoomManager` — в `app/transport/` (инфраструктура: соединения,
  список игроков, адресная рассылка).
- `Room` оборачивает `Game`, но не реализует правила.
- «Соединение» (WebSocket + логин) — отдельная сущность транспорта,
  уже реализована в `ConnectionManager`.

Обоснование: правила должны тестироваться без сети; комнаты — это
инфраструктура. Соответствует `VISION.md` §8 (Layered + Domain vs.
transport boundary).

**Открытый вопрос:** начинаем проектировать архитектуру (пункт 3 карты)
или сразу переходим к UI и проектируем архитектуру по ходу?

**Не реализовано (кандидаты на развитие):**
- игровая логика: раздача, ходы, отбой, взятие, козырь, конец игры;
- доменные сущности `Player`, `Game`, `Table`, `GameState`;
- комнаты/лобби (сейчас один общий broadcast);
- персистентность (БД) и реальная аутентификация (JWT/сессии);
- типизированные схемы сообщений (Pydantic-модели вместо `dict`);
- расширение тестов: транспорт, интеграционные WebSocket-тесты.

**Замечания по коду:**
- `ConnectionManager.USERS` — тестовые данные в коде, вынести в конфиг/БД.
- `broadcast` использует `except Exception` — стоит сузить.
- `app/domain/__init__.py` и `app/transport/__init__.py` пусты — можно
  реэкспортировать публичный API.
